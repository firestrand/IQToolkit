# MariaDB package acquisition and static qualification probe

This GOTCHA scope advances the required MariaDB compatibility investigation from [accepted source/readiness evidence](modernization-mariadb-probe.md) to authentic packages and static inspection. It preserves MySql.Data 26.7.0 and the existing provider. It does not authorize SDK operations, an engine start, a database query, public API changes or promotion to supported status.

## Goals and measurable objectives

Acquire the six exact MariaDB 12.3.3 Ubuntu Noble packages and four missing Ubuntu dependencies identified by authentic indexes: ten archives totaling 14,237,418 bytes. Require every archive's exact size and SHA256, plus the MariaDB SHA512 values, to match the accepted acquisition profile. Inspect the real archive format, control metadata, licenses, bootstrap scripts as text, payload members and ARM64 ELF dependencies. Record concrete remaining prerequisites before preparing an engine experiment. A package/index discrepancy or missing origin is a failed prerequisite, not a reason to substitute another release or driver.

## Tasks and termination

Two independent read-only tasks investigate exact release routing and installed parser/ELF capabilities in disjoint handoffs. Root integrates the evidence, expands MDB0 in the implementation plan and prepares source/commands/profile/ownership bounds. Independent planning and source review, followed by review of the exact dispatch packet, precede any archive acquisition or extraction. After acquisition, verify and independently review the raw archive identities before dependent static qualification. Inspect only through the installed system tools and Python runtime; never execute package payloads or maintainer scripts.

Terminate with actual archive/static outcomes, source/index/binary preservation, settled subprocesses, inactive retained evidence and an ATLAS report, or a preserved bounded failure. Do not imply whole-project closure or stage changes while the broader verification gate is failed/stopped.

## Capabilities and off-limits actions

Allowed during preparation: read source, standards, official public metadata and installed tool/source/version records; write only task-owned documents, controls and ignored evidence. Later accepted packets may make fixed public HTTPS package reads, parse archives, materialize bounded regular-file payload copies privately and run installed read-only archive/ELF inspection commands. Links remain recorded metadata during static qualification; no symlink, hardlink, special-device or package execution is required for this stage.

Off limits: SDK/restore/build/publish; `mariadbd`, `mariadb`, provider/driver calls or any downloaded program; `ldd` on payloads; maintainer scripts; package installation, privileged operations, system services, Docker permission changes, DDL or application data; credentials, paid services, production dependencies, public contracts, Git staging/commit/push/tag/publication, or retries under previously exhausted packets. Static inspection cannot qualify startup, ABI compatibility, authentication or SQL behavior.

### Runtime acceptance stages

`accepted()` has three distinct call contexts, and directory membership must match the context rather than a single frozen post-rebind set. The supervisor's initial preflight accepts only the complete twelve-file reconciled baseline: the nine reconciliation/subject files plus the three exact current acceptance receipts. Immediately after the supervisor writes `started.json`, the worker's startup preflight accepts precisely that baseline plus one valid mode-0400 start receipt whose packet digest and process/deadline fields satisfy the launch contract. Each runtime entry must be a no-follow regular file with an allowed mode and size; unknown names, gaps, duplicate representations, symlinks, excessive bytes, or malformed receipts fail closed. Existing telemetry, archive, worker and packet validators remain responsible for content and success classification; admitting a name to the lifecycle set never implies that its content passed.

Post-rebind review acceptance uses the current frozen review manifest for its planning/source/exact-packet reports. The reconciliation receipt remains bound to the manifest that authorized the rebind and is independently bound by its digest. A later manifest is valid only when its exact rows reproduce the current operation-input catalog and all three independent approvals agree on that manifest, current source/profile/packet, and reconciliation digest. Comparing the later approvals to the older rebind manifest incorrectly makes a legitimate fresh review impossible; accepting stale or mixed-epoch reports remains prohibited.

Private deterministic fixtures must cover all three production call sites: clean ready state; worker startup with the authentic-shaped `started.json`; preservation with bounded partial and complete runtime evidence. Preservation must allow a missing worker receipt after an early worker startup failure. The fixtures must also refuse an unknown sidecar, a missing/gapped/duplicate event sequence, invalid modes/types/size ceilings, a start receipt with stale packet or process binding, and a review receipt bound to the rebind manifest instead of the current review manifest. Snapshot names, bytes and modes around refusals. Run under normal and optimized Python; never launch `_worker`, issue HTTP, or mutate the live prepared attempt.
